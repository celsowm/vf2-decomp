# decomp.dev progress reporting

`vf2-decomp` publishes an objdiff-compatible **Report v2** for decomp.dev even
though objdiff itself does not support Intel i960 code comparison.

The report is generated by `tools/decomp_dev_report.py` and uploaded by
`.github/workflows/decomp-dev.yml` as the artifact:

```text
vf2_21_report
└── report.json
```

This is the artifact naming/layout expected by decomp.dev.

## What the percentage means

The public percentage is intentionally conservative. It measures **program-ROM
bytes that are represented by fully recovered, explicitly bounded entries in
`decomp/i960/functions.csv`** against the complete VF2 2.1 i960 program-ROM
payload.

The denominator is derived from the four `maincpu` EPR files in
`config/vf2_v22_roms.csv`:

```text
4 × 0x20000 = 0x80000 = 524,288 bytes
```

Only entries whose status is currently one of:

```text
recovered
recovered-rom-anchor
```

and whose `address`/`end` form a positive explicit range contribute matched
bytes. Overlapping recovered ranges are merged before counting.

`candidate` entries with an explicit range are published as known incomplete
units. All other program-ROM bytes are represented by the synthetic
`unrecovered_or_partial_program_rom` unit.

This deliberately does **not** count repeated execution. A loop that executes a
recovered instruction one million times still contributes the instruction's ROM
bytes once. The much larger dynamic differential numbers in `docs/STATUS.md`
therefore remain a different metric: they prove behavioral coverage and runtime
continuity, not static decompilation byte coverage.

Observed prefixes and branch-only recoveries are also excluded from matched
bytes until their static extents are explicit enough to count honestly. This
means the decomp.dev percentage will initially understate the amount of useful
recovered C, by design.

## Categories

The generator assigns tracked units to stable progress categories such as:

- Boot / initialization
- Scheduler / tasks
- Camera
- Gameplay / input / collision
- Video / graphics
- Objects / osage
- Audio
- Runtime / other
- Unrecovered / partial program ROM

Categories are derived from the function name so adding a new fully recovered
bounded entry to `decomp/i960/functions.csv` updates the report automatically.

## Generate locally

No ROM files are required.

```sh
python3 tools/decomp_dev_report.py --check
python3 tools/decomp_dev_report.py --output build/decomp-dev/report.json
python3 -m json.tool build/decomp-dev/report.json >/dev/null
```

The generator uses only committed metadata and never embeds ROM bytes, hashes of
working copies, local paths, snapshots, or proprietary assets into the report.

## Registering the project

Once a successful `decomp.dev progress` run exists on `master`:

1. Sign in to https://decomp.dev/ with the GitHub account that administers
   `celsowm/vf2-decomp`.
2. Open https://decomp.dev/manage/new.
3. Select `celsowm/vf2-decomp`.
4. Select the `vf2_21` report/version discovered from the
   `vf2_21_report` artifact.
5. Create the project.

The decomp.dev GitHub App may then be enabled for completion notifications and
PR progress comments. Installing the App alone does not register the project;
the report artifact is the discovery/ingestion contract.

## Report format

The JSON follows objdiff's current Report v2 protobuf JSON mapping. In
particular, 64-bit integer fields such as `total_code`, `matched_code`, `size`
and `address` are emitted as JSON strings, while percentages and 32-bit counters
are JSON numbers.
