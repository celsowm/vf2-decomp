# v0732k: RETRACTION — the fighter bases were wrong, the 0xd00 block was dual-base all along

**This note retracts v0732h, v0732i and v0732j, and the correction v0732h
made to the v0730 taint note.** It also fixes a committed bug that had been
propagating the wrong answer since v0729.

## The error

Every dual-base result from v0729 onward used these fighter bases:

```text
fighter0 = 0x510000
fighter1 = 0x520000
```

The **measured** bases, recorded in the `fa_game_info` scenario metadata
(`out/state8-positive.json`, generated by
`decomp/i960/tools/make_game_info_probe_scenario.py` from the measured
`0x164ac` boundary), are:

```text
fighter0        = 0x00510980
fighter0_flags  = 0x00510b24      (offset 0x1a4)
fighter0_selector = 0x00511380    (offset 0xa00)
fighter1        = 0x00512980
fighter1_flags  = 0x00512b24      (offset 0x1a4)
fighter1_selector = 0x00513380    (offset 0xa00)
```

The real fighter1 struct is at **0x512980**, not 0x520000. A window of
`0x520000..0x522000` does not contain it, so **every** fighter1 access was
invisible, and every candidate silently reported `base_count == 1`.

I took the wrong pair from an illustrative snippet in the v0730 handoff
runbook and did not check it against the scenario metadata. The v0732h note
even printed a scenario's metadata showing the right values in a nearby
command, and I still used the runbook's numbers.

## What is actually true

`out/trace-both.jsonl` — named "both" because it covers **both** fighters —
is genuinely dual-base. Measured directly, with no window tricks:

```text
fighter0 window 0x510980: 144 distinct offsets, 341 events
fighter1 window 0x512980: 144 distinct offsets, 341 events
shared offsets:          144
```

**All 144 offsets, from both bases, with identical event counts.** The
project's own tools agree:

```text
$ python tools/python/infer_structs.py out/trace-both.jsonl \
    --base fighter0=0x510980 --base fighter1=0x512980 --window 0x2000

+0x01a4  bases=fighter0,fighter1  R=70 W=0  sizes=4Bx70
  provenance: fighter0<-out/trace-both.jsonl; fighter1<-out/trace-both.jsonl
+0x0000  bases=fighter0,fighter1  R=60 W=0  sizes=4Bx60
+0x01a8  bases=fighter0,fighter1  R=4  W=0  sizes=2Bx4
...  (every candidate is base_count 2)
```

```text
$ frontier.contiguous_fighter_blocks(width=4, min_count=2, min_length=120)
offset 0x00000d00 end 0x00000ee0 len 120 bytes 480
reads 480 writes 480 base_count 2 ip_overlap 1.0
top_ips ['0x0002399c', '0x00023a38']
```

**The block is dual-base and is promoted.** The v0704/v0706 discipline is
satisfied on every axis: same offset, same access width (4 B), same guest
IPs (`0x2399c` + `0x23a38`), balanced read/write role, 240 reads + 240
writes *per base*.

### The v0729 block is the same block

The v0729 note reported the block at `0x1680..0x1860` from base `0x510000`.
From the correct base `0x510980` it reads `0x0d00..0x0ee0`. The difference
is exactly `0x980` — the offset between the wrong and right fighter0 base.
Everything else in the v0729 record was right: length 120, 480 bytes,
`ip_overlap` 1.0, IPs `0x2399c` + `0x23a38`, and "reads/writes are balanced:
240 of each per 120 offsets".

**So the v0729 note was correct about the block and wrong only about its
base.** The block was never single-base. It was measured correctly and
reported from a displaced origin.

## The committed bug

`tools/python/p1_real_trace_demo.py` (ctest #117) hardcoded the wrong bases
*and* asserted the wrong result:

```python
FIGHTER_BASES = [0x510000, 0x520000]
EXPECTED_OFFSET = "0x00001680"
EXPECTED_BLOCK_BASE_COUNT = 1  # fighter1-inclusive trace not on master
```

`tools/python/test_p1_real_trace_demo.py` repeated the assertion. So a
green ctest entry was **locking in `base_count == 1`** — the "pending
promotion" was an enforced invariant, not an open question. That is how the
error survived three notes and survived me.

Both files are now corrected: the measured bases, the block at `0x0d00`,
`base_count == 2`, plus new pins on `reads == 480` / `writes == 480` and on
the per-offset roll-up reporting `144 of them dual-base`. The test now
**asserts the promotion**, so a regression to 1 fails loudly. 13/13 factory
ctest entries pass.

The synthetic unit suites (`test_frontier.py`, `test_factory_chain.py`,
`test_infer_structs.py`) also use `0x510000`/`0x520000`, but those traces are
authored by the tests themselves, so they are self-consistent and are left
alone. Only the real-corpus demo was wrong.

## The four-slices-it-took lesson

v0732h, v0732i and v0732j were each internally consistent, each ran real
tools, each produced plausible-looking numbers, and each was wrong in the
same way. What would have caught it in one step:

- **Check a constant against its measured source.** `0x510000` looked like a
  round number. The scenario metadata was sitting in `out/` with the real
  values, and one `json.load` would have shown them.
- **A "pending" result that has a green test asserting it is a smell.**
  `base_count == 1` was pinned by ctest #117 with a comment calling it
  pending. A pending result should be *unasserted*, so a change in evidence
  flips it loudly.
- **Be suspicious of a negative that explains everything.** "0 of 264" is
  exactly the kind of result that invites you to reframe the whole problem.
  The reframe ("state, not tooling") was the most expensive thing I could
  have concluded, and it came entirely from my own bad input.
- **A negative needs the same provenance as a positive.** I said that in
  v0732j and then did not apply it to the bases I was feeding in.

## Standing correction

Any analysis that names a fighter base must cite where it came from. The
only measured pair in this repo is the scenario metadata's. Derive from:

```sh
python -c "import json;print(json.load(open('out/state8-positive.json'))['metadata'])"
```

`0x510000` / `0x520000` are **not** fighter bases in VF2.
